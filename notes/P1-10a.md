# P1-10a: Menu.Dock.Details_D (B7 + B8) - dock dynamic rows actually update

Date: 2026-10-19 · Phase 1, branch `phase1-bugfix` (working tree on `main`)

## Script: plugin.LI.FDN.Menu.Dock.Details_D (v1.0 -> v2)

### Assumptions
- The dock dynamic flag the player toggles in Configuration is stored at `[6][2]` ("dynamic.dock"); `[6][1]` belongs to the retired `dynamic.dock.list` UI whose Config row is commented out. Main.Menu and Config already use `[2]`, so this script was simply reading the wrong index (B7).
- The token in `[20]` is written by Main.Menu only when it STARTs a `_D` updater (P1-09a): one bump at menu open, and one per new updater. So "token changed since I started" reliably means an older updater must exit (B8).
- Re-reading `al.LI.FDN.event` each loop pass is the same pattern Main.Menu uses; it's cheap (one global read) versus a 1000-5000 ms wait.
- A per-ware dynamic-menu global is named with **textid=5000**; textid=5001 names the credits block only. Confirmed by cross-referencing Write sub, Update sub and the reader `Menu.Dock.Details` (L067 credits = 5001; L101 per-ware row = 5000). DC.Details_D already uses 5000 in both subs, which confirms intent.

### Questions for Matt
None - both check items from the card were confirmed and resolved:
1. **Check 1 (does L057 close the loop?): YES.** `return null` is a real exit (not an if-branch), so the first bare `end` closes `while [TRUE]`. The update sub at old-L061 sat after that, meaning it ran once and never again. Fixed by moving `gosub Update.Menu.Global.Sub:` inside the loop.
2. **Check 2 (5001 vs 5000 in the per-ware pointer?): L138 was WRONG.** It used textid=5001 with a ware argument, but the reader (`Menu.Dock.Details` L101) reads textid=5000 for each ware row. Writes went to a global nobody read, so live rows never updated even after fix #1. Changed to 5000 (tagged `* v9.01 B8`) per approval.
